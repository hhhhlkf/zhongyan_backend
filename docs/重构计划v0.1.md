# 中研无人机遥感应急平台重构计划 v0.1

## 1. 版本定位

### 1.1 重构目标

本次 v0.1 重构的目标，是将现有围绕“采集、处理、传输、贴图展示”的系统，升级为面向无人机遥感应急场景的半自主化任务平台。

系统核心对象调整为：

```text
Mission -> Task -> Command/Event -> Asset
```

其中 `Task` 是最重要的运行单元。采集、处理、传输、坐标计算、图层发布、示范回放、Agent 分析，都应被建模为可追踪、可重试、可审计、可回放的 Task。

### 1.2 设计原则

1. 本地和边缘优先：系统主要部署在本地中心节点，采集设备、图像处理模型、小模型可运行在无人机端或边缘板卡上。
2. 事件驱动：Kafka 作为统一事件总线，替换传统轮询和同步调用堆叠。
3. 高可用与可恢复：任务状态、命令、事件、资产都必须可追踪，失败后可以定位、重试或人工介入。
4. Agent 统一化：不拆成多个常驻 Agent，而是构建一个统一的 `Zhongyan Agent Orchestrator`，通过工具、策略和权限路由完成不同能力。
5. 兼容现有系统：现有后端接口和前端工作台不一次性推倒，优先通过兼容层纳入 Task 编排，再逐步替换内部实现。

### 1.3 当前系统事实

根据现有 `zhongyan_backend` 与 `zhongyan_web`：

- 后端当前为 Spring Boot 2.7.5 + Java 11。
- 后端当前未启用数据库，`application.yml` 排除了 `DataSourceAutoConfiguration`。
- 当前设备控制主要依赖 SSH 远程命令、共享目录、文件系统、UDP 数据文件和本地静态资源目录。
- 当前实时性主要由前端 `setInterval` 轮询 `/v2/data/recent`、`/v2/uav/info/realtime` 等接口完成。
- 前端当前为 Vue 3 + Vite + Mars3D/Cesium + Element Plus + Pinia。
- 已存在采集、处理、传输、历史数据、实时无人机显示、贴图图层等基础能力，但任务模型、事件模型、数据库模型和 Agent 工具体系还未系统化。

## 2. 目标技术栈

### 2.1 后端基础栈

- Java 21。
- Spring Boot 4.x。
- Spring Web MVC 或 WebFlux 按模块选择，不强制全量响应式。
- Java 虚拟线程用于阻塞型 I/O 接口，例如设备 SSH、文件读取、对象存储访问。
- 长任务和设备任务使用有界线程池，避免无限制并发拖垮节点。
- Spring Security + JWT + RBAC，替换当前 `permitAll` 的临时安全策略。

### 2.2 数据与空间能力

- PostgreSQL：业务主库。
- PostGIS：空间几何、四角坐标、多边形、空间索引。
- pgvector：Agent RAG 向量检索。
- MinIO：遥感大图、预览图、模型输出、报告、PDF、视频等大文件对象存储。
- GeoServer：发布 GeoTIFF、ImageMosaic、WMS、WMTS 图层。

### 2.3 事件与缓存

- Kafka：统一事件总线，承载任务事件、设备命令、资产事件、无人机遥测、Agent 审计。
- Redis：缓存、分布式锁、在线状态、短期热点状态、接口限流。
- WebSocket/SSE：后端向前端推送实时任务状态、日志、遥测和 Agent 流式输出。

### 2.4 前端技术栈

- Vue 3 + Vite 保留。
- Mars3D/Cesium 保留为主地图和三维展示底座。
- Element Plus 保留为基础组件库。
- Pinia 继续作为状态管理。
- 逐步引入 TypeScript，优先从 Task、Mission、Asset、Agent 相关模块开始。
- Web Worker 用于大列表、坐标转换、轨迹处理等计算密集型前端逻辑。

### 2.5 AI 技术栈

- 本地模型优先：vLLM 或 Ollama，提供 OpenAI-compatible API。
- 云端模型可选：只处理低敏复杂推理，必须经过脱敏策略。
- Spring AI：统一接入 Chat Model、Embedding Model、Vector Store、Tool Calling、RAG、流式回复。
- Tool Gateway：统一封装 Agent 可调用工具，做权限、审计、幂等和人工确认。

## 3. 核心领域模型

### 3.1 Mission

`Mission` 表示一次完整的应急任务、外场作业、演示案例或算法验证流程。

典型示例：

- 资兴灾害应急采集任务。
- 洞庭湖遥感演示任务。
- 甘肃无人机处理回传任务。

建议字段：

| 字段 | 含义 |
| --- | --- |
| missionId | 任务组唯一编号 |
| name | 任务名称 |
| scenarioType | 场景类型，如 emergency、demo、training、test |
| region | 任务区域，可保存省市区、中心点、空间范围 |
| status | Mission 状态 |
| priority | 优先级 |
| createdBy | 创建人 |
| createdAt | 创建时间 |
| startedAt | 开始时间 |
| endedAt | 结束时间 |
| description | 备注说明 |

Mission 状态建议：

- `DRAFT`：草稿。
- `ACTIVE`：执行中。
- `PAUSED`：暂停。
- `COMPLETED`：完成。
- `CANCELLED`：取消。
- `FAILED`：任务组失败。

### 3.2 Task

`Task` 表示系统内可执行的最小业务任务，是 v0.1 的核心。

建议字段：

| 字段 | 含义 |
| --- | --- |
| taskId | Task 唯一编号 |
| missionId | 所属 Mission |
| taskType | Task 类型 |
| status | 当前状态 |
| priority | 优先级 |
| deviceId | 绑定设备，如相机、板卡、无人机、传输节点 |
| modelId | 绑定模型 |
| inputAssets | 输入资产列表 |
| outputAssets | 输出资产列表 |
| config | Task 配置 JSON |
| progress | 进度，0-100 |
| createdAt | 创建时间 |
| updatedAt | 更新时间 |
| startedAt | 开始时间 |
| endedAt | 结束时间 |
| createdBy | 创建人或 Agent |
| errorCode | 错误码 |
| errorMessage | 错误信息 |

Task 类型：

- `CAPTURE`：采集任务。
- `PROCESS`：处理任务。
- `TRANSFER`：传输任务。
- `PUBLISH_LAYER`：发布 GIS 图层任务。
- `GENERATE_PREVIEW`：生成预览图任务。
- `CALCULATE_GEO_BOUNDARY`：计算图像地理边界任务。
- `DEMO_PLAYBACK`：示范案例回放任务。
- `AGENT_ANALYSIS`：Agent 分析任务。
- `REPORT_GENERATION`：报告生成任务。

### 3.3 TaskAttempt

`TaskAttempt` 记录 Task 的每一次执行尝试，用于失败重试、设备掉线恢复、执行节点切换和审计。

建议字段：

| 字段 | 含义 |
| --- | --- |
| attemptId | 尝试编号 |
| taskId | 所属 Task |
| attemptNo | 第几次尝试 |
| executorNode | 执行节点 |
| startedAt | 开始时间 |
| endedAt | 结束时间 |
| result | 执行结果 |
| errorCode | 错误码 |
| errorMessage | 错误信息 |
| rawLogObjectKey | 原始日志对象存储 key |

TaskAttempt 规则：

1. 每次真正开始执行 Task 时创建一条 Attempt。
2. 重试不会覆盖旧 Attempt。
3. 失败原因、设备输出、模型日志必须绑定到 Attempt。
4. Agent 诊断时优先读取最近一次失败 Attempt。

### 3.4 TaskCommand

`TaskCommand` 表示一次对 Task 或设备的命令请求。

建议字段：

| 字段 | 含义 |
| --- | --- |
| commandId | 命令编号 |
| taskId | 关联 Task |
| missionId | 关联 Mission |
| deviceId | 目标设备 |
| commandType | 命令类型 |
| payload | 命令参数 JSON |
| idempotencyKey | 幂等键 |
| requestedBy | 请求来源，用户或 Agent |
| requiresApproval | 是否需要人工确认 |
| approvedBy | 审批人 |
| approvedAt | 审批时间 |
| createdAt | 创建时间 |
| dispatchedAt | 下发时间 |
| completedAt | 完成时间 |
| status | 命令状态 |

命令类型：

- `START`：开始。
- `STOP`：停止。
- `PAUSE`：暂停。
- `RESUME`：恢复。
- `RETRY`：重试。
- `CANCEL`：取消。
- `CONFIRM`：确认。
- `ROLLBACK`：回滚。

高风险命令：

- 停止设备。
- 重启模型。
- 删除数据。
- 覆盖图层。
- 发布图层。
- 启动采集。
- 启动处理。
- 启动传输。

这些命令必须进入 `WAITING_APPROVAL`，经人工确认后才允许写入 `device-commands`。

### 3.5 TaskEvent

`TaskEvent` 表示 Task 生命周期中的事件，是任务回放、前端实时状态、Agent 审计和故障诊断的基础。

建议字段：

| 字段 | 含义 |
| --- | --- |
| eventId | 事件编号 |
| taskId | 关联 Task |
| missionId | 关联 Mission |
| eventType | 事件类型 |
| statusBefore | 变更前状态 |
| statusAfter | 变更后状态 |
| payload | 事件内容 JSON |
| timestamp | 发生时间 |
| source | 事件来源 |

事件类型：

- `CREATED`：已创建。
- `QUEUED`：已入队。
- `COMMAND_SENT`：命令已下发。
- `RUNNING`：执行中。
- `PROGRESS_CHANGED`：进度变化。
- `ASSET_CREATED`：产物生成。
- `FAILED`：失败。
- `RETRYING`：重试中。
- `COMPLETED`：完成。
- `CANCELLED`：取消。
- `APPROVAL_REQUIRED`：需要人工确认。
- `APPROVED`：已确认。
- `TIMEOUT`：超时。

TaskEvent 规则：

1. 所有状态变化必须产生 TaskEvent。
2. 前端任务中心只订阅事件，不依赖重复查询来感知状态变化。
3. Agent 的所有工具调用结果也要沉淀为事件。
4. TaskEvent 同时写入数据库和 Kafka，数据库用于查询，Kafka 用于实时分发。

### 3.6 TaskDependency

`TaskDependency` 表示 Task 之间的依赖关系。

建议字段：

| 字段 | 含义 |
| --- | --- |
| dependencyId | 依赖编号 |
| taskId | 当前 Task |
| dependsOnTaskId | 依赖的 Task |
| dependencyType | 依赖类型 |
| requiredStatus | 依赖 Task 必须达到的状态 |
| createdAt | 创建时间 |

典型依赖：

- 处理任务必须等待采集资产生成。
- 坐标计算任务必须等待图像文件到达。
- 图层发布任务必须等待坐标计算完成。
- 报告生成任务必须等待采集、处理和传输完成。
- 示范回放任务必须等待底图和案例资产准备完成。

### 3.7 TaskResourceLease

`TaskResourceLease` 表示资源占用，用于防止同一设备被并发冲突调用。

建议字段：

| 字段 | 含义 |
| --- | --- |
| leaseId | 锁编号 |
| taskId | 占用该资源的 Task |
| resourceType | 资源类型，如 camera、board、model、transfer-node |
| resourceId | 资源编号 |
| leaseStatus | 锁状态 |
| expiresAt | 过期时间 |
| createdAt | 创建时间 |

实现规则：

1. PostgreSQL 保存资源占用最终状态。
2. Redis 负责短期分布式锁。
3. 任务失败、超时、取消时必须释放资源。
4. 锁过期后需要由后台恢复任务扫描器判断是否自动释放。

### 3.8 TaskAsset

`TaskAsset` 绑定 Task 的输入输出产物。

建议字段：

| 字段 | 含义 |
| --- | --- |
| taskId | Task 编号 |
| assetId | Asset 编号 |
| assetRole | 资产角色 |
| createdAt | 创建时间 |

资产角色：

- `INPUT`：输入。
- `OUTPUT`：输出。
- `PREVIEW`：预览。
- `LOG`：日志。
- `LAYER`：图层。
- `REPORT`：报告。

### 3.9 Asset

`Asset` 表示所有可管理数据资产。

建议字段：

| 字段 | 含义 |
| --- | --- |
| assetId | 资产编号 |
| assetType | 资产类型 |
| name | 名称 |
| objectKey | MinIO 对象 key |
| previewObjectKey | 预览对象 key |
| geometry | PostGIS geometry |
| layerUrl | GeoServer 图层地址 |
| sourceTaskId | 来源 Task |
| tags | 标签 |
| metadata | 元数据 JSON |
| createdAt | 创建时间 |

资产类型：

- `IMAGE`。
- `GEOTIFF`。
- `VIDEO`。
- `PDF`。
- `DOCUMENT`。
- `MODEL_RESULT`。
- `LOG`。
- `REPORT`。
- `LAYER`。

## 4. Task 生命周期

### 4.1 标准状态

| 状态 | 含义 |
| --- | --- |
| DRAFT | 已创建但未提交 |
| WAITING_APPROVAL | 高风险命令等待人工确认 |
| QUEUED | 已入队，等待消费者执行 |
| DISPATCHING | 正在下发到设备、模型或传输程序 |
| RUNNING | 任务执行中 |
| WAITING_ASSET | 等待文件、坐标、模型结果或传输结果到达 |
| POST_PROCESSING | 生成预览、计算边界、发布图层、写入资产库 |
| COMPLETED | 成功完成 |
| FAILED | 失败，保留错误原因 |
| RETRYING | 按策略重试 |
| CANCELLED | 人工取消 |
| TIMEOUT | 超过最大等待时间 |

### 4.2 状态流转

常规流转：

```text
DRAFT
  -> QUEUED
  -> DISPATCHING
  -> RUNNING
  -> WAITING_ASSET
  -> POST_PROCESSING
  -> COMPLETED
```

高风险命令流转：

```text
DRAFT
  -> WAITING_APPROVAL
  -> QUEUED
  -> DISPATCHING
  -> RUNNING
```

失败重试流转：

```text
RUNNING
  -> FAILED
  -> RETRYING
  -> QUEUED
```

人工取消流转：

```text
QUEUED/RUNNING/WAITING_ASSET
  -> CANCELLED
```

超时流转：

```text
DISPATCHING/RUNNING/WAITING_ASSET
  -> TIMEOUT
  -> FAILED 或 RETRYING
```

### 4.3 生命周期规则

1. 每次状态变化必须写入 `task_event`。
2. 每次状态变化必须发送 Kafka `task-events`。
3. 所有设备命令必须携带 `commandId` 与 `idempotencyKey`。
4. 同一 `deviceId` 的命令通过 Kafka key 分区保证顺序消费。
5. 高风险命令必须人工确认。
6. Task 重试必须创建新的 `TaskAttempt`。
7. Task 不能直接删除，只允许逻辑归档，避免破坏审计链路。

## 5. Task 类型细化

### 5.1 CAPTURE 采集任务

输入：

- 相机类型：RGB、HSI、LLT 等。
- 相机名称。
- 相机开始指令。
- 相机停止指令。
- 相机检查指令。
- 板卡地址。
- 采集模式：连续采集、定时采集、定量采集。
- 采集间隔。
- 采集数量。
- 是否绑定无人机遥测。
- 是否生成预览图。
- 是否实时贴图。

输出：

- 原始采集图片。
- 压缩预览图。
- 四角坐标 poly。
- 采集日志。
- 实时贴图事件。
- 采集资产记录。

执行流程：

1. 创建 CAPTURE Task。
2. 检查相机和板卡可用性。
3. 获取资源锁，防止同一相机重复启动。
4. 如需人工确认，则进入 `WAITING_APPROVAL`。
5. 下发 START 命令到 Kafka `device-commands`。
6. 设备消费者执行 SSH 或边缘 API。
7. Task 进入 `RUNNING`。
8. 文件事件消费者监听新图片。
9. 新文件到达后写入 MinIO，并创建 Asset。
10. 生成预览图。
11. 调用坐标计算 Task。
12. 前端通过 `asset-events` 与 `task-events` 实时显示。
13. 停止采集后释放资源锁。

关键规则：

- 采集开始前清理当前临时列表，防止旧数据混入。
- 采集图片层级低于处理结果层，高于灾害底图层。
- 如果图片过大，前端默认展示预览图，原图按需加载。
- 如果坐标计算失败，资产仍入库，但标记为不可贴图。

### 5.2 PROCESS 处理任务

输入：

- 模型名称。
- 模型启动命令。
- 模型停止命令。
- 模型输入格式。
- 模型输出格式。
- 输入资产。
- 输出尺寸要求。
- GPU 或边缘节点约束。
- 模型参数 JSON。

输出：

- 模型结果图。
- 模型结果预览。
- 模型运行日志。
- 处理图层。
- 处理资产记录。

执行流程：

1. 创建 PROCESS Task。
2. 校验输入资产是否存在。
3. 获取模型或板卡资源锁。
4. 下发模型 START 命令。
5. Task 进入 `RUNNING`。
6. 等待模型输出文件。
7. 输出文件到达后创建 Asset。
8. 生成预览图和坐标。
9. 触发贴图事件。
10. 任务完成后释放资源锁。

关键规则：

- 模型启动和停止都必须走 TaskCommand。
- 模型长任务必须有心跳或日志进度。
- 处理结果层永远覆盖采集图层。
- 处理失败时保留输入资产、模型日志和 Attempt 记录。

### 5.3 TRANSFER 传输任务

输入：

- 本地板卡 IP。
- 远端板卡 IP。
- 传输命令。
- 停止传输命令。
- 文件集合。
- 传输策略。
- 超时时间。

输出：

- 传输进度。
- 传输速率。
- 成功文件日志。
- 失败文件日志。
- 传输事件流。

执行流程：

1. 创建 TRANSFER Task。
2. 检查本地和远端节点连通性。
3. 获取传输节点资源锁。
4. 下发 START 命令。
5. 消费传输进度事件。
6. 更新 Task progress。
7. 文件完成后写入 `asset-events`。
8. 传输结束或停止后释放资源。

关键规则：

- 传输状态优先通过 Kafka 推送。
- 当前共享目录速率读取可作为兼容兜底。
- 传输失败必须记录失败文件和失败原因。
- 重试时只重试失败文件，不重复传输成功文件。

### 5.4 CALCULATE_GEO_BOUNDARY 坐标计算任务

输入：

- 图片 Asset。
- 无人机经纬度。
- 无人机高度。
- 无人机姿态：yaw、pitch、roll。
- 相机水平 FOV。
- 相机垂直 FOV。
- 地面高程。
- 可选设备精确四角坐标。

输出：

- 四角坐标 poly。
- PostGIS geometry。
- 坐标计算日志。

执行流程：

1. 优先检查资产是否已有设备精确坐标。
2. 如果没有，读取匹配时间范围内的 UAV telemetry。
3. 根据姿态、高度、FOV、地面高程计算四角坐标。
4. 写入 PostGIS。
5. 写入 poly 文件或兼容格式。
6. 发送 `asset-events` 通知前端可贴图。

关键规则：

- 优先使用设备直接给出的精确四角坐标。
- 缺失时才计算。
- 计算失败不阻塞资产入库，但标记 `geoStatus=FAILED`。
- 坐标计算必须可复算，保留输入参数快照。

### 5.5 PUBLISH_LAYER 图层发布任务

输入：

- GeoTIFF 或遥感大图 Asset。
- 空间范围。
- 图层名称。
- 样式配置。
- 切片策略。

输出：

- GeoServer layerName。
- WMS URL。
- WMTS URL。
- 图层元数据。

执行流程：

1. 校验遥感数据格式。
2. 将原始大图存入 MinIO。
3. 元数据和空间范围写入 PostgreSQL/PostGIS。
4. 调用 GeoServer 发布图层。
5. 写入 Asset layerUrl。
6. 发送图层发布事件。

关键规则：

- 大图不直接存入 PostgreSQL。
- PostGIS 只保存空间索引和元数据。
- GeoServer 负责图层发布，不负责业务状态。
- 发布图层属于高风险动作，需要人工确认。

### 5.6 GENERATE_PREVIEW 预览生成任务

输入：

- 原始图片或模型结果 Asset。
- 目标长边。
- 目标大小。
- 最低质量。
- 保留数量。

输出：

- 预览图 Asset。

关键规则：

- 前端实时展示默认使用预览图。
- 原图只在查看详情、下载、图层发布时加载。
- 预览生成失败不影响原始资产入库。

### 5.7 DEMO_PLAYBACK 示范回放任务

输入：

- 示范案例。
- 省、市、灾害区域。
- 底图 Asset。
- 采集资产列表。
- 处理资产列表。
- 播放顺序。
- 是否显示无人机。
- 是否显示航线。
- 是否显示扫描锥体。
- 是否显示传输基站动画。

输出：

- 前端动画事件流。
- 回放状态。

执行流程：

1. 选择示范案例。
2. 地图视角从省级移动到市级，再移动到灾害区域。
3. 创建无人机模型。
4. 按资产编号顺序播放采集图和处理图。
5. 绘制航线和扫描锥体。
6. 可选展示数据回传基站动画。
7. 结束后清理临时图形。

关键规则：

- 回放不改变原始资产。
- 回放临时图层必须可一次性清理。
- 编号以文件名数字或任务生成顺序为准。
- 处理结果展示层级高于采集结果。

### 5.8 AGENT_ANALYSIS Agent 分析任务

输入：

- 用户问题。
- Mission 上下文。
- Task 上下文。
- Asset 列表。
- 设备状态。
- 日志。
- RAG 检索结果。

输出：

- 分析结论。
- 建议动作。
- 待确认命令。
- 报告草稿。
- 系统优化建议。

关键规则：

- Agent 可自主执行查询、总结、统计、生成计划。
- Agent 不可绕过 Tool Gateway。
- Agent 对启动、停止、删除、发布等高风险动作只能生成待确认命令。
- 所有工具调用必须进入 `agent-events`。

### 5.9 REPORT_GENERATION 报告生成任务

输入：

- Mission。
- Task 时间线。
- 采集资产。
- 处理资产。
- 传输日志。
- Agent 分析结论。

输出：

- 任务总结报告。
- 灾害研判报告。
- 数据清单。
- 系统优化建议文档。

关键规则：

- 报告必须引用数据来源。
- 报告草稿可由 Agent 生成，但最终确认由用户完成。
- 报告文件存入 MinIO，元数据入 Asset。

## 6. Kafka 事件设计

### 6.1 Topic 划分

| Topic | 用途 | Key |
| --- | --- | --- |
| device-commands | 设备、模型、传输控制命令 | deviceId |
| task-events | Task 生命周期事件 | taskId |
| asset-events | 文件到达、预览生成、坐标生成、图层发布 | assetId |
| uav-telemetry | 无人机高频遥测 | uavId |
| agent-events | Agent 推理、工具调用、人工确认、审计 | conversationId 或 missionId |
| system-dlt | 死信事件 | originalKey |

### 6.2 device-commands

用途：

- 承载相机控制。
- 承载模型启动和停止。
- 承载传输启动和停止。
- 承载设备状态检查。

设计规则：

- key 使用 `deviceId`。
- 同一设备的命令顺序消费。
- 消费者执行前必须检查 `idempotencyKey`。
- 成功或失败都必须写入 `task-events`。

示例事件：

```json
{
  "commandId": "cmd-001",
  "taskId": "task-001",
  "missionId": "mission-001",
  "deviceId": "camera-rgb-01",
  "commandType": "START",
  "payload": {
    "captureMode": "forever",
    "interval": 5
  },
  "idempotencyKey": "task-001:start:camera-rgb-01",
  "requestedBy": "user:admin",
  "requiresApproval": true,
  "createdAt": "2026-04-27T16:00:00+08:00"
}
```

### 6.3 task-events

用途：

- 前端任务中心实时更新。
- Mission 时间线。
- Agent 分析和复盘。
- 故障诊断。

示例事件：

```json
{
  "eventId": "evt-001",
  "taskId": "task-001",
  "missionId": "mission-001",
  "eventType": "RUNNING",
  "statusBefore": "DISPATCHING",
  "statusAfter": "RUNNING",
  "payload": {
    "message": "RGB camera started successfully"
  },
  "timestamp": "2026-04-27T16:00:05+08:00"
}
```

### 6.4 asset-events

用途：

- 通知前端新图片到达。
- 通知预览图已生成。
- 通知四角坐标已生成。
- 通知 GeoServer 图层已发布。

关键事件类型：

- `ASSET_UPLOADED`。
- `PREVIEW_GENERATED`。
- `GEO_BOUNDARY_CALCULATED`。
- `LAYER_PUBLISHED`。
- `ASSET_FAILED`。

### 6.5 uav-telemetry

用途：

- 高频记录无人机姿态和位置。
- 支撑实时航线展示。
- 支撑坐标计算。
- 支撑回放。

建议字段：

- `uavId`。
- `missionId`。
- `lon`。
- `lat`。
- `alt`。
- `yaw`。
- `pitch`。
- `roll`。
- `velo`。
- `timestamp`。

### 6.6 agent-events

用途：

- 记录 Agent 推理过程。
- 记录工具调用。
- 记录人工确认。
- 记录风险拦截。
- 形成审计链路。

关键事件：

- `USER_MESSAGE_RECEIVED`。
- `PLAN_CREATED`。
- `TOOL_SELECTED`。
- `TOOL_CALL_STARTED`。
- `TOOL_CALL_COMPLETED`。
- `TOOL_CALL_BLOCKED`。
- `APPROVAL_REQUESTED`。
- `APPROVAL_CONFIRMED`。
- `ANSWER_STREAMED`。

### 6.7 system-dlt

所有消费失败、格式错误、命令超时、不可恢复异常进入 `system-dlt`。

DLT 事件必须包含：

- 原 Topic。
- 原 partition。
- 原 offset。
- 原 key。
- 原 payload。
- 失败原因。
- 失败消费者。
- 失败时间。

Agent 诊断工具可以读取 DLT，但不能直接删除 DLT 记录。

## 7. 统一 Agent 架构

### 7.1 总体设计

系统只保留一个统一 Agent：

```text
Zhongyan Agent Orchestrator
```

它不是多个 Agent 的简单集合，而是统一的任务理解、工具路由、风险控制和信息整理入口。

### 7.2 内部四层能力

#### Planner

职责：

- 理解用户意图。
- 判断用户是在查询、操作、诊断、规划还是生成报告。
- 将复杂目标拆成 Mission 和 Task 草案。
- 生成可确认的任务计划。

示例：

用户输入：“帮我对资兴区域执行一次采集、处理和回传，并生成报告。”

Planner 输出：

- 创建 Mission。
- 创建 CAPTURE Task。
- 创建 PROCESS Task，依赖 CAPTURE。
- 创建 TRANSFER Task，依赖 PROCESS。
- 创建 REPORT_GENERATION Task，依赖前三者。
- 需要人工确认启动采集、处理、传输。

#### Tool Router

职责：

- 根据 Planner 结果选择工具。
- 对工具参数做结构化。
- 调用 Tool Gateway。
- 将工具结果反馈给模型和前端。

工具分类：

- 任务工具。
- 设备工具。
- 数据工具。
- 诊断工具。
- 报告工具。

#### Policy Guard

职责：

- 判断工具是否允许调用。
- 判断是否需要人工确认。
- 判断用户权限是否足够。
- 阻断危险动作。

行为边界：

- 可自主执行：查询、总结、统计、生成计划、读取公开状态。
- 需确认执行：启动采集、启动处理、启动传输、停止设备、删除数据、发布图层。
- 禁止执行：直接 SSH、直接删除对象存储、直接写数据库、绕过后端接口。

#### Memory/RAG

职责：

- 检索历史任务。
- 检索设备文档。
- 检索灾害数据。
- 检索日志。
- 检索用户偏好和优化建议。

存储：

- 原文存 PostgreSQL 或 MinIO。
- 向量存 pgvector。
- 结构化任务数据直接查 PostgreSQL。

### 7.3 Tool Gateway

Tool Gateway 是 Agent 调用系统能力的唯一入口。

每个工具必须定义：

- 工具名称。
- 工具描述。
- 输入 JSON Schema。
- 输出 JSON Schema。
- 权限要求。
- 风险等级。
- 是否需要人工确认。
- 是否允许 Agent 自主执行。
- 审计策略。

示例工具：

```text
mission.create
task.create
task.query
task.retry
task.cancel
device.checkCamera
device.checkBoard
device.queryUavTelemetry
command.createStartCapture
asset.search
asset.stats
case.search
layer.query
diagnosis.readTaskLog
diagnosis.analyzeKafkaDlt
report.generateDraft
optimization.appendSuggestion
```

### 7.4 Agent 输出形态

前端 Agent 面板需要展示：

- 对话流式回复。
- 任务计划卡片。
- 工具调用轨迹。
- 引用数据来源。
- 风险提示。
- 人工确认按钮。
- 执行结果摘要。
- 自动生成的系统优化建议。

### 7.5 Agent 审计

每次 Agent 行为必须记录：

- 会话 ID。
- 用户输入。
- Planner 结果。
- 工具调用名称。
- 工具参数。
- 工具结果。
- 是否触发人工确认。
- 是否被 Policy Guard 阻断。
- 输出摘要。

审计数据写入：

- PostgreSQL。
- Kafka `agent-events`。

## 8. 前端重构设计

### 8.1 页面结构

前端保持 Mars3D 大地球作为主视觉和主工作区。

建议布局采用“地图优先、上左右集中控制”的工作台结构。默认状态下不要同时展开所有板块，避免主地图视野被挤压；任务中心、Agent、事件、日志、回放控制都集中放在顶部、左侧或右侧，不设置常驻底部面板。

```text
┌────────────────────────────────────────────────────────────┐
│ 顶部状态与操作栏：任务、设备、Kafka、无人机、告警、回放控制       │
├───────┬───────────────────────────────────────────┬────────┤
│ 折叠栏 │ Mars3D/Cesium 地图主视图                    │ 折叠栏 │
│ 任务   │ 贴图、航线、扫描锥体、图层、临时动画           │ Agent  │
│ 资产   │                                           │ 事件   │
└────────────────────────────────────────────────────────────┘
```

### 8.2 面板空间管理

整体原则：

- 地图是主工作区，默认至少保留 70% 可视宽度。
- 顶部承载全局状态、当前任务进度、告警入口、连接状态和回放控制。
- 左侧承载任务中心、资产列表、图层开关和 Mission 切换。
- 右侧承载 Agent、事件时间线、任务日志、工具轨迹和待确认动作。
- 底部不放置常驻功能、折叠入口或时间线，底部空间尽量留给地图视野。
- 所有面板都支持最小化、固定、悬浮和关闭。
- 面板展开时使用遮罩式或抽屉式覆盖地图边缘，不整体压缩地图到不可用。
- 用户可保存个人布局偏好，如“指挥模式”“地图最大化”“Agent 辅助”“调试模式”。

面板尺寸建议：

- 顶部状态栏高度控制在 48-64px。
- 左侧任务窄栏宽度 56-72px，展开宽度 320-420px。
- 右侧 Agent/事件窄栏宽度 56-72px，展开宽度 360-480px。
- 顶部告警、进度和回放控制使用图标、短文本和下拉弹层，不向下扩展成大面板。
- 小屏或低分辨率下，左侧任务中心和右侧 Agent/事件面板同一时间最多展开一个。

交互策略：

- 常态只显示任务状态、告警数量、无人机位置、连接状态等摘要。
- 用户点击 Mission、Task、告警、Agent 回复时，再从左侧或右侧展开对应详情。
- 任务日志、工具调用轨迹、资产列表默认分页或虚拟滚动，不一次性铺满面板。
- 高风险确认动作从右侧轻量确认抽屉弹出，确认后自动收起。
- 事件时间线作为右侧面板 Tab 或顶部告警弹层展示，不在底部展开。
- 演示回放和实时采集时进入“地图最大化模式”，仅保留顶部必要控制按钮。

### 8.3 任务中心面板

功能：

- Mission 列表。
- Task DAG。
- Task 状态。
- Task 进度。
- Task 日志。
- Task 资产产物。
- 失败重试。
- 人工确认。

Task 卡片展示：

- Task 类型。
- 当前状态。
- 进度。
- 设备或模型。
- 输入资产。
- 输出资产。
- 最近事件。
- 错误原因。

展示规则：

- 默认只显示当前 Mission、运行中 Task、失败 Task 和待确认命令。
- 历史 Task、资产产物、详细日志放入二级抽屉或详情页。
- Task DAG 默认显示简化拓扑，节点点击后再展开依赖详情。
- 多任务并发时优先展示异常、等待确认、正在执行的任务。
- 列表必须支持搜索、筛选、分页或虚拟滚动，避免长列表挤满面板。

### 8.4 实时推送

优先使用 WebSocket 或 SSE：

- 订阅 `task-events`。
- 订阅 `asset-events`。
- 订阅 `uav-telemetry`。
- 订阅 Agent 流式输出。

弱网降级：

- 断线后自动重连。
- 多次失败后切换 HTTP 增量轮询。
- 恢复连接后根据最后 eventId 补齐事件。

### 8.5 地图层级

固定层级：

```text
灾害底图层
  < 采集贴图层
  < 处理结果层
  < 当前任务动画层
  < 交互标注层
```

规则：

- 处理结果永远覆盖采集结果。
- 采集和处理结果永远覆盖灾害底图。
- 示范回放临时图层结束后必须清理。
- 大图优先通过 GeoServer 图层加载。
- 普通图片可通过四角坐标贴图。

### 8.6 Agent 面板

功能：

- 统一对话入口。
- 显示工具调用步骤。
- 显示引用数据。
- 显示待确认动作。
- 可把 Agent 计划转为 Mission/Task。
- 可导出 Agent 生成的报告草稿。

展示规则：

- 默认以右侧窄栏或悬浮按钮存在，不强制常驻大面板。
- 对话、工具轨迹、引用数据、待确认动作分 Tab 展示，避免全部堆在同一视图。
- Agent 回复较长时提供摘要优先视图，完整推理过程放入可展开区域。
- 工具调用轨迹默认折叠，只突出当前执行步骤、失败步骤和待确认步骤。
- 用户进入“Agent 辅助模式”时再展开完整面板；退出后恢复地图最大化。

## 9. 后端重构设计

### 9.1 模块划分

建议模块：

```text
com.zhongyan.uav.mission
com.zhongyan.uav.task
com.zhongyan.uav.command
com.zhongyan.uav.event
com.zhongyan.uav.asset
com.zhongyan.uav.device
com.zhongyan.uav.geo
com.zhongyan.uav.agent
com.zhongyan.uav.audit
com.zhongyan.uav.realtime
```

### 9.2 任务编排模块

职责：

- Mission 创建和查询。
- Task 创建和查询。
- Task 状态机。
- Task 依赖调度。
- TaskAttempt 管理。
- TaskEvent 写入。
- 高风险命令审批。

### 9.3 设备适配器模块

职责：

- 封装当前 SSH 命令。
- 封装相机控制。
- 封装模型控制。
- 封装传输控制。
- 统一设备状态检查。

迁移策略：

- 第一阶段保留 `application.yml` 中现有设备配置。
- 第二阶段将设备配置迁移入数据库。
- 第三阶段支持设备插件化注册。

### 9.4 配置存储与版本管理

相机配置、模型配置、传输配置属于系统“可调用能力配置”，必须有明确存储边界，不能散落在前端、本地临时 JSON、Kafka 消息或任务日志中。

明确指示：

- 主存储：PostgreSQL。
- 敏感信息：密码、token、私钥、云端模型 API Key 不直接明文存储，优先存 Vault/KMS；v0.1 如果暂不引入密钥系统，则使用后端加密字段保存，并通过环境变量提供加密主密钥。
- 运行态缓存：Redis 只缓存配置摘要、在线状态、健康检查结果和短期锁，不作为最终数据源。
- 事件流：Kafka 只记录“配置创建、配置变更、配置验证、配置启停”等事件，不保存配置主数据。
- 任务快照：Task 创建时必须把当时使用的相机配置、模型配置、传输配置复制到 `task.config`，形成执行快照。
- 大文件：模型权重、模型说明文档、设备手册、测试样例、配置附件存 MinIO，PostgreSQL 只保存对象 key 和元数据。
- 本地配置文件：`application.yml` 只保留系统启动所需的 bootstrap 配置，以及旧配置迁移种子；正式注册后的相机和模型配置以数据库为准。

相机配置存储内容：

- `device_config`：通用设备信息，如设备编号、设备类型、IP、端口、所属边缘节点、认证方式、在线状态。
- `camera_config`：相机专属信息，如相机类型、检查命令、开始采集命令、停止采集命令、输出目录、文件命名规则、FOV、是否支持设备原生四角坐标。
- `config_version`：配置版本，每次修改相机命令、FOV、输出目录、认证方式都必须生成新版本。

模型配置存储内容：

- `model_config`：模型名称、模型类型、运行节点、启动命令、停止命令、健康检查命令、输入格式、输出格式、输入目录、输出目录、GPU 要求、运行环境、参数 schema。
- `model_artifact`：模型权重、README、测试样例、容器镜像、依赖说明等大文件的 MinIO 对象 key。
- `config_version`：模型配置版本，每次修改命令、输入输出格式、运行环境、模型权重引用都必须生成新版本。

配置验证结果存储：

- `config_validation`：记录连通性测试、命令 dry-run、输入输出检查、输出目录检查、测试样例运行结果。
- 验证通过后配置状态为 `READY`。
- 验证失败后配置状态为 `CONFIG_ERROR`，失败日志进入 MinIO，错误摘要写入 PostgreSQL。

Task 使用配置的规则：

- 创建 `CAPTURE Task` 时只引用 `cameraConfigId` 和 `cameraConfigVersion`。
- 创建 `PROCESS Task` 时只引用 `modelConfigId` 和 `modelConfigVersion`。
- Task 提交执行前，后端读取配置版本并生成 `task.config` 快照。
- 任务执行期间禁止直接读取“最新配置”替代快照，避免任务中途配置变化导致不可复现。
- 如果用户要使用新配置，必须创建新 Task 或重试时明确选择新版本。

## 14. 关键风险与建议

### 14.1 Kafka 引入复杂度

Kafka 能明显提升事件回放和高吞吐能力，但部署和运维复杂度高于简单队列。

建议：

- v0.1 只引入必要 topic。
- 先让采集、处理、传输三个主链路事件化。
- 遥测高频数据独立 topic，避免挤占任务控制事件。

### 14.2 设备控制可靠性

当前设备控制依赖 SSH 和字符串输出判断，容易受网络、脚本输出和环境影响。

建议：

- 先封装 Device Adapter。
- 每个命令都记录原始输出。
- 推动边缘端提供 HTTP/gRPC 控制服务，逐步替代 SSH。

### 14.3 Agent 过度自动化风险

无人机采集、模型处理、数据删除、图层发布都可能影响真实业务。

建议：

- Agent 先从辅助决策和信息整理开始。
- 高风险工具必须人工确认。
- 所有工具调用必须可审计。

### 14.4 前端一次性大改风险

现有前端已有较多 Mars3D、贴图、无人机动画逻辑。

建议：

- 先新增任务中心和 Agent 面板。
- 保留现有大屏入口。
- 逐步替换轮询为实时事件。

## 15. v0.1 默认假设

1. v0.1 使用 Kafka + Redis，不使用 RabbitMQ。
2. Agent 数量收敛为一个统一 Orchestrator，通过工具和策略区分能力。
3. Task 是后续采集、处理、传输、数据管理、示范回放和 Agent 自动化的统一执行模型。
4. 系统部署以本地和边缘为主，云端模型只作为可选增强。
5. 现有系统不一次性推倒，优先通过兼容层把旧接口纳入 Task 编排，再逐步替换内部实现。
6. 已注册相机配置和模型配置的主数据存 PostgreSQL，附件和模型权重存 MinIO，运行态缓存放 Redis，配置变更事件进 Kafka。
7. Task 执行必须使用配置版本快照，不允许执行中读取“最新配置”替代历史快照。
8. 原 `重构计划.md` 保留，本文档作为 v0.1 正式重构计划。
